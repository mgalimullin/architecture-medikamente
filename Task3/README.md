### **Задание 3. Оценка Data Encryption at Rest and In Transit**
### **1. Классификация данных и необходимость защиты**

Прежде чем выбирать инструменты, классифицируем все данные, обрабатываемые в системе, по нескольким параметрам:
*   **Состояние:** Хранение (At Rest) или Передача (In Transit).
*   **Категория:** PII, Медицинские, Финансовые, и т.д.
*   **Уровень критичности:** Критичный, Высокий, Средний.
*   **Профиль риска:** Основные угрозы (кража носителя, перехват трафика, инсайдер).

| Данные | Категория (152-ФЗ) | Уровень критичности | Состояние | Профиль риска | Необходимость защиты |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Прямые идентификаторы пациентов (ФИО, паспорт, телефон, email, адрес)** | ПДн (Специальные, если есть паспорт) | **Критичный** | Хранение (At Rest) | Кража физического сервера/диска, SQL-инъекция, доступ DBA. | **Обязательна.** Шифрование — единственный способ защитить данные от чтения при компрометации хранилища. |
| **Медицинские данные (диагнозы, анализы, заключения)** | ПДн (Специальная категория) | **Критичный** | Хранение (At Rest) | Кража носителя, утечка файлов, инсайдер. | **Обязательна.** Шифрование файлов и записей в БД. |
| **Данные аутентификации (пароли, хэши)** | - | **Критичный** | Хранение (At Rest) | Компрометация БД, подбор паролей. | **Обязательна.** Только криптографическое хэширование с солью. |
| **Платёжные данные (суммы, даты, статусы)** | ПДн (в контексте услуг) | **Высокий** | Хранение (At Rest) | Компрометация БД, внутреннее мошенничество. | **Обязательна.** Шифрование БД. |
| **Квази-идентификаторы (дата рождения, пол)** | ПДн (Общая категория) | **Средний** | Хранение (At Rest) | Деанонимизация при комбинации с другими данными. | **Рекомендована.** Шифрование или псевдонимизация. |
| **Логи аудита** | Могут содержать ПДн | **Высокий** | Хранение (At Rest) | Сокрытие следов атаки, подделка логов. | **Обязательна.** Обеспечение неизменности (иммутабельности) и шифрование. |
| **Все данные** | Все категории | **Критичный/Высокий** | Передача (In Transit) | Перехват трафика (MitM-атаки), прослушивание Wi-Fi. | **Обязательна.** Предотвращает перехват данных в пути. |

### **2. Реализация базовых инструментов защиты (Encryption at Rest and In Transit)**

#### **2.1. Шифрование при передаче (Data Encryption in Transit)**

| Сегмент сети / Коммуникация | Инструмент / Протокол | Конфигурация / Реализация |
| :--- | :--- | :--- |
| **Клиент <-> API Gateway** (Пользовательские порталы, мобильное приложение) | **TLS 1.3** (минимум 1.2) | Настройка **API Gateway** (например, Kong) на прием только HTTPS-трафика. Использование сертификатов от доверенного центра (Let's Encrypt). Перенаправление всего HTTP-трафика на HTTPS на уровне конфигурации Gateway. <br> *Ссылка: [Руководство по безопасности TLS](https://github.com/ssllabs/research/wiki/SSL-and-TLS-Deployment-Best-Practices)* |
| **Взаимодействие микросервисов (Service-to-Service)** | **mTLS (mutual TLS)** или **TLS** | Внедрение **Service Mesh** (например, **Istio** или **Linkerd**) в кластере Kubernetes. Service Mesh автоматически шифрует весь трафик между подами и управляет выдачей сертификатов для каждого сервиса. Это реализуется через конфигурацию (YAML) Control Plane, без изменения кода сервисов. |
| **Сервисы <-> Базы данных** | **TLS** | Базы данных (PostgreSQL, ClickHouse) должны быть настроены на прием только TLS-соединений. В `postgresql.conf` необходимо установить `ssl = on` и указать пути к сертификатам. Все клиенты (сервисы на Java) должны быть сконфигурированы на использование SSL (`?ssl=true&sslmode=require` в строке подключения). |
| **Сервисы <-> Внешние системы (Лаборатория)** | **TLS / mTLS** | API-эндпоинты внешних систем должны вызываться строго по HTTPS. Для особо чувствительных данных необходимо настроить взаимную аутентификацию (mTLS), где клиент (интеграционная шина) и сервер (лаборатория) подтверждают свою подлинность сертификатами. |
| **Внутренняя сеть (VPN)** | **WireGuard** или **OpenVPN** | Весь трафик между филиалами и центральным кластером, а также трафик удаленных сотрудников (администраторов) должен проходить через зашифрованный VPN-туннель. Настройка VPN-сервера и клиентов — это чисто конфигурационная задача. |

#### **2.2. Шифрование при хранении (Data Encryption at Rest)**

| Хранилище | Инструмент / Метод | Конфигурация / Реализация |
| :--- | :--- | :--- |
| **Базы данных (PostgreSQL)** | **Transparent Data Encryption (TDE) / Column-level encryption** | 1. **На уровне диска/блока:** Использовать возможности облачного провайдера или LUKS для шифрования томов, на которых развернуты БД. Это защищает от кражи дисков. <br> 2. **На уровне БД (рекомендуется):** Использовать модуль **`pgcrypto`**. Чувствительные столбцы (например, `passport_number`, `phone`) должны храниться в зашифрованном виде. Расшифровка происходит на стороне приложения (Java-сервиса) с использованием ключей, хранящихся в **Vault**. <br> *Ссылка: [Документация pgcrypto](https://www.postgresql.org/docs/current/pgcrypto.html)* |
| **Файловое хранилище (MinIO)** | **Server-Side Encryption (SSE)** | MinIO поддерживает шифрование на стороне сервера с использованием собственного менеджера ключей (KES) или внешнего KMS. Включается через переменные окружения или конфигурационные файлы при старте сервера. Все загружаемые объекты автоматически шифруются. <br> *Ссылка: [MinIO Encryption](https://min.io/docs/minio/linux/operations/server-side-encryption.html)* |
| **Резервные копии (Backups)** | **Шифрование на стороне клиента** | Скрипты резервного копирования (например, `pg_dump`) должны передавать данные утилите шифрования (например, `gpg` или `openssl enc`) перед отправкой в хранилище (S3). Ключи шифрования хранятся в Vault. Это гарантирует, что даже бэкапы, украденные из S3, не будут скомпрометированы. |
| **Виртуальные машины и диски** | **Шифрование дисков (LUKS)** | На всех серверах (физических и виртуальных) системные и данные разделы должны быть зашифрованы с использованием **LUKS (Linux Unified Key Setup)**. Парольная фраза для разблокировки диска при старте должна вводиться через безопасную консоль или храниться на отдельном защищенном ключе-носителе. |
| **Журналы (логи) аудита** | **Шифрование и иммьютабельность** | Хранилище логов (например, Elasticsearch) должно быть настроено на шифрование индексов (если поддерживается). Также необходимо настроить политики **WORM (Write Once, Read Many)**, чтобы никто, включая администраторов, не мог изменить или удалить запись аудита. |

### **3. Автоматизированный контроль за данными (Data Activity Monitoring)**

| Средство контроля | Инструмент | Цель | Реализация |
| :--- | :--- | :--- | :--- |
| **Управление ключами шифрования (KMS)** | **HashiCorp Vault** | Централизованное хранение, ротация и аудит доступа к ключам шифрования. Ни один ключ не должен храниться в коде или на диске сервера в открытом виде. | Vault разворачивается в кластере. Сервисы получают ключи для расшифровки данных по запросу, с использованием его токенов. Все обращения к Vault логируются. Настройка политик доступа к ключам делается в конфигурации Vault. |
| **Мониторинг целостности сертификатов** | **Prometheus + Blackbox Exporter** | Отслеживание сроков действия TLS-сертификатов. Если сертификат истекает, система должна автоматически генерировать алерт, чтобы избежать отказа в обслуживании и уязвимостей. | Blackbox Exporter настраивается на периодическую проверку HTTPS-эндпоинтов. Метрики об истечении срока собираются в Prometheus, где настроены правила алертинга. |
| **Data Loss Prevention (DLP) на уровне хранилищ** | **OpenDLP** или политики MinIO | Контроль за попытками выгрузки больших объемов данных или данных с высоким уровнем критичности (по тегам). | В MinIO настраиваются политики, запрещающие анонимный доступ и ограничивающие скорость скачивания для определенных бакетов или типов объектов. |
| **Аудит доступа к данным** | **Elasticsearch + Auditbeat / pgAudit** | Сбор логов о том, кто и когда обращался к данным. Логи должны быть защищены от изменений. | **pgAudit** включается в PostgreSQL для логирования всех запросов. Auditbeat собирает логи с файловых серверов и приложений. Все стекается в Elasticsearch, где настроены дашборды для визуализации и алерты на аномалии (например, пользователь запросил 10000 записей в 3 часа ночи). |

### **4. Реестр программных и аппаратных средств для защиты данных**

| Инструмент | Тип | Назначение | Место в архитектуре | Конфигурация |
| :--- | :--- | :--- | :--- | :--- |
| **HashiCorp Vault** | Программное (KMS) | Управление секретами, ключами шифрования, паролями БД. Централизованная выдача динамических учетных данных. | Уровень безопасности / Уровень данных | Vault конфигурируется через файлы HCL. Интеграция с Kubernetes для автоматической выдачи токенов подам. |
| **Istio / Linkerd** | Программное (Service Mesh) | Обеспечение mTLS между микросервисами, сбор телеметрии, управление трафиком. | Уровень приложений (K8s) | Устанавливается в кластер K8s. Политики безопасности (AuthorizationPolicy) и правила mTLS задаются декларативно в YAML-манифестах. |
| **Kong / Nginx** | Программное (API Gateway) | Терминация TLS, маршрутизация, rate limiting, сбор метаданных для аудита. | Периметр безопасности | Настройка через конфигурационные файлы (nginx.conf) или декларативные конфиги Kong (YAML). |
| **MinIO** | Программное (S3-хранилище) | Объектное хранилище с поддержкой SSE и тегирования. | Уровень данных | Настройка переменных окружения для KMS, создание бакетов и политик через `mc` клиент или YAML. |
| **PostgreSQL + pgcrypto + pgAudit** | Программное (БД) | Хранение данных с шифрованием столбцов и детальным аудитом доступа. | Уровень данных | Активация модулей через `CREATE EXTENSION`. Настройка параметров в `postgresql.conf`. |
| **LUKS** | Программное (Шифрование дисков) | Шифрование разделов на физических серверах и ВМ. | Инфраструктура (ОС) | Настраивается при установке ОС или с помощью скриптов инициализации. |
| **WireGuard** | Программное (VPN) | Создание защищенных каналов связи между филиалами и для удаленного доступа. | Инфраструктура (Сеть) | Конфигурация через `.conf` файлы на сервере и клиентах. |
| **Prometheus + Blackbox Exporter** | Программное (Мониторинг) | Мониторинг доступности и сроков действия сертификатов. | Уровень мониторинга | Настройка таргетов для Blackbox в `prometheus.yml`. Правила алертинга также в YAML. |
| **ELK Stack (Elasticsearch, Logstash, Kibana)** | Программное (Логирование) | Централизованный сбор, хранение и анализ логов аудита. | Уровень мониторинга | Конфигурация битов (Auditbeat, Filebeat) для отправки логов. Индексы в Elasticsearch настраиваются под требования по ротации и шифрованию. |
